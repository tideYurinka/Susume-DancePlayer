# 三份安装身份：正式版 · 测试版 · 调试版

装出去的 Susume 原本只有一份**安装身份**，发出去的包也只有一种——正式版。开发时要看真机，`flutter run` 装的是同名、同签名（本机有 `android/key.properties` 时）的调试包，于是它就地接替手机上那份正式版，并接着写同一个数据目录；想给特定测试者一份新包时也没有第二条路，`workflow_dispatch` 出的那份与正式版同身份、同签名、同版本号，装上去仍是原地升级。两条入口都会动到正式版的数据，而这不是纪律问题——是模型里只有一份身份。

于是立三份：**正式版**（`top.yurinka.susume`）、**测试版**（`top.yurinka.susume.test`）、**调试版**（`top.yurinka.susume.debug`），由 Gradle 的 flavor（`prod` / `beta`）与 `debug` 构建类型相乘得到。正式版的身份与签名一个字不改，已装用户照常升级；日常 `flutter run` 落到调试版，再也碰不到手机上那份正式版。三份身份各持 `/data/user/0/<applicationId>/` 下的一整套数据——舞库、标注、统计、计划、日志、缓存，彼此读不到对方。这正是「测试版不影响正式版的数据」在 Android 上唯一天然成立的做法：不共享目录，就没有共享数据的可能。

测试版那份 flavor 叫 `beta` 而不是 `test`：AGP 把 `test` 前缀留给单元测试源集（`ProductFlavor names cannot start with 'test'`）。这是构建侧的命名约束，与词表术语**测试版**无关——安装身份的后缀仍是 `.test`，版本名仍带 `-test`。

测试版与正式版还有两处必须分开。**签名**：测试版用与正式签名分开的一把测试 keystore，于是测试包之间能原地覆盖升级，而正式版的升级凭据不落到测试者手里；缺测试钥时构建直接失败，不回落 debug 签名——debug keystore 逐机生成，回落会让测试者只能卸载重装，就地升级这条不变量会静默失效。**更新**：**版本清单**里没有身份字段，测试版读同一份清单只会被推一份正式身份的安装包，所以测试身份下整条更新链路停用——不自动检查，**版本行**也不再给检查入口，新测试包由作者直接递给测试者。

版本号那一处刻意不动：构建号仍只来自 `pubspec.yaml`，测试版的身份标记只落在版本名（`-test` 后缀）与诊断面（构建标识）上。同号同签名允许覆盖安装，于是测试包之间照样原地升级，不必另立一套编号；而 prerelease 形式的版本名过不了发布门的正则，身份标记因此只能落在构建产物一侧。依据见 `docs/research/2026-10-05-android-versioncode-and-flutter-versioning.md`。

代价是测试版从零开始：它读不到正式版的舞库、标注与统计，要搬只能走已有的 **susume 包**与**备份**导出导入；测试期若抬高过文档版本，搬回正式版还会被**文档地板**棘轮判成只读读。这是隔离的价钱，已接受。

## Considered Options

- **同一个安装身份，用版本号与开关区分**（正式版里给一个「加入测试」的开关给全员、公开一个固定 versionCode、再用语义区分「这个版本可降级」）：改动面横跨安装、更新与数据三条链，且都压在正式版那一份身份上，走错一步的代价是已装用户的正式版数据。留待真需要「正式版内切换渠道」时再议。
- **只把 debug 构建换个身份**：解决自己调试顶掉正式版，但测试者拿不到 release 模式的包（慢、带调试标记），也没有一条可原地升级的稳定签名。
- **测试版与正式版共用一把正式 keystore**：少管一把钥，却把正式版的升级凭据交到了测试者手里。
- **测试版回落 debug 签名**：debug keystore 逐机生成，换一台机器构建出的测试包签名就不同，测试者必须卸载重装，测试数据一起丢。
- **给测试版第二份版本清单**：要再养一条发布链路与一处新地址，与**更新源**「地址此后不变、是判断有没有新版的唯一来源」的口径相冲；测试包由作者直接发，暂不需要。
- **靠卸载重装切换**：唯一不用改构建配置的路，但每次切换都丢数据——正是要避免的那件事。

## Consequences

- 仓库里从此有四份 applicationId 组合（`prod` / `beta` 两 flavor × `debug` / `release` 两构建类型）；Flutter 还有一个 `profile` 构建类型，它不带后缀，于是 `betaProfile` 与 `betaRelease` 同身份——profile 只作本地诊断，不对外。写死安装身份的护栏要改成「一个正式身份 + 一个已知后缀白名单」，而不是断言全仓只有一处。
- 构建多了一层 flavor：正式发布必须显式 `--flavor prod`，测试包必须显式 `--flavor beta`；`pubspec.yaml` 的 `default-flavor: prod` 让日常 `flutter run` 与不带参数的构建仍有确定落点。
- **用哪把钥只由 flavor 决定**：构建类型的 `signingConfig` 优先级高于 flavor，若写在构建类型上，测试版会被悄悄签成正式钥而 Gradle 不报错——只有 `./gradlew :app:signingReport` 看得见。缺测试凭据时由一道只挂在测试版打包路径上的前置检查直接失败，不靠 AGP 兜底（实测 APK 路径上的签名版本任务缺钥也照样通过）。
- 测试者的正式版数据留在正式版里；测试版里的成果要带走只能经导出/导入，且可能回灌成只读读。
- 两个 App 都注册了 `.susume` 与 octet-stream 的入站 filter，系统选择器会同时列出它们——靠应用名（「Susume」与「Susume 测试版」）分辨，包可能被导进另一个 App。
- 测试包与正式包共用系统相册这一个写入目的地（帮助配图导出），两者都只写不读；分享出去的文件落在用户自选的位置，同名可能互相覆盖。
