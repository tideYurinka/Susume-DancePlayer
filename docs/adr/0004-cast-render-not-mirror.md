# ADR-0004：投屏只做「投屏渲染 + 推片 + 遥控」，不做镜像

投屏这件事在 Android 上有两条根本不同的路：**把画面镜像过去**，或**把一份自足的文件交给电视自己播**。前者的吸引点很实在——手机上的镜像、循环、倍速、数拍、拍声会原样出现在电视上；但它在本平台上**做不到**：第三方 App 无法自己发起 Miracast（`WifiDisplay`/`MediaRouter` 那套是 hidden + signature 权限），Google Cast 的屏幕镜像同样只有系统入口；而本项目播放器的画面是 media_kit 渲进 Android Surface、再以 Flutter 外部纹理上屏的，**不在 Flutter 的画面树里**，所以"把画面抓下来自己推"也不成立（对祖先做 `RepaintBoundary.toImage()` 只能拿到纹理占位矩形；仓里唯一的取帧手段是让 ffmpeg 重新解码文件）。

因此决定：**投屏 = 投屏渲染 + 推片 + 遥控**。手机按当前设置与标注渲染出一份**投屏副本**（画面含全局镜像、局部镜像片段、取景、备注贴纸与**数拍的逐拍静态数字**；音轨含拍声；范围为**首线→尾线**），经本机局域网递给**接收端**自己解码播放；手机转为遥控（播放/暂停/进度/音量/学习段/**投屏倍速档**）。**时间类标注**（分段线、半拍线、八拍锚点）不进画面，它们以「遥控跳到那一段」的形式留下；**节拍动画也不进副本**——呈现类只烤逐拍静态数字（摆锤与动画一像素都不进，理由见下条 Consequences）。

**不做屏幕镜像**（本平台对第三方 App 封死了这条路），但**在投屏态顶栏留一枚「系统镜像」入口**，把用户送到系统的「投屏 / 无线显示」设置（`Settings.ACTION_CAST_SETTINGS`，public API since 21，minSdk 24 恒可用；无 Activity 接时降级到显示设置，再不行给一句「短暂提示」）。点它**先断开投屏**再跳——否则电视上会一边放我们的副本、一边被系统镜像顶掉，两份画面打架。它不是本功能的一部分，只是那些"我们这条路走不通"的时刻（手边只有 Chromecast、没有 DLNA 接收端、或者就要整屏）的明示退路；两条路的能力边界要在入口的提示文案里一句话说清。

## Considered Options

- **屏幕镜像**：本平台做不到（隐藏 API + 系统签名权限）；且拍声与画面会错开 100–300ms。正因为做不到，投屏态顶栏才留了一枚只负责"送用户过去"的**系统镜像**入口，而不是把镜像写成我们自己的能力。
- **从播放器抓帧自己推流**：画面是外部纹理，抓不成帧；改走 MediaProjection 整屏录制再自研协议，是另一个量级的工程且没有接收端。
- **Media3 Transformer（GPU 合成 + 硬编）**：许可更省（Apache-2.0）、720p 实测吞吐好得多（Google 自测约 7.7–8.4× 实时），但 Media3 **没有镜像效果**，时间窗要靠 `TextureOverlay` 子类自写——等于把 ffmpeg 已经白送的东西重造一遍。留作吞吐不过关时的退路。
- **软件 x264（换 `_min_gpl` 变体）**：只在 +4.3 MB/ABI，且本仓已是 GPL-3.0、许可上不构成障碍，但没必要——**已出货的 `ffmpeg-kit-min` 里本来就有 `h264_mediacodec` 硬编与原生 AAC**，零依赖、零体积增长。
- **商业投屏 SDK（乐播一类）**：能顺带拿到镜像与倍速播控，但要按量付费、闭源、且把能力边界交给对方。

## Consequences

- **投屏副本比源视频多一代有损压缩**（必然），画面在电视上略软于手机本地播放。
- **渲染是分钟级的**：这是本功能最大的一笔代价，缓存与"先投后渲"因此不是优化而是必需品。
- **投屏期手机不能改已被渲染的设置**（镜像/取景/贴纸/数拍/倍速）：要改就先断开、改完再投。投屏态**只读**、底排槽位整排不出现，是这条决定的直接后果。
- **电视上那份与手机上那份会不一致**：数拍数字是**渲染那一刻**按数拍锚点链算出来的，烤死之后不随遥控跳段重锚定。这也是节拍动画不进副本的原因——烤死的动画与跳段后的重锚定会互相打脸，呈现类因此只烤逐拍静态数字。这是已知且已接受的偏差。
- **倍速绕开了接收端**：靠一档一份副本、换文件实现，代价是切换时的起播等待（约 1–3 秒）与 `Seek` 精度由接收端决定。
- 继承一条本仓原有的依赖事实：`ffmpeg_kit_flutter_new_min` 的上游已归档、现在用的是社区 fork，**分发时需在 NOTICE 记明来源与版本**，以便日后替换或重建。
- **两条路并存**：顶栏那枚**系统镜像**入口让用户在"我们渲染的副本"与"系统整屏镜像"之间选。走系统镜像时，本项目的镜像、取景、贴纸、数拍、拍声与倍速都随整屏上电视，代价是镜像延迟、手机屏必须亮着、控制层也一起上电视。这个取舍由入口的提示文案承担；系统镜像那条路**不归我们管**，我们不为它的质量做任何保证。

## 渲染路线关卡（#24）实测与结论

关卡问的是这一条：**继续用已链接的 ffmpeg CLI（`h264_mediacodec` 硬编），还是改 GPU 合成路线（Media3 Transformer）**。计时入口与全部读数留档在 [`docs/research/2026-10-08-cast-render-route-gate.md`](../research/2026-10-08-cast-render-route-gate.md)（入口：`tool/cast_render_bench_host.dart`、`tool/cast_render_bench.sh`；固定输入：30s/1080p/30fps + 一张带 alpha 的单帧贴纸 + 一条 120bpm 拍声；输入哈希随读数留档）。

**结论：路线不变，继续用已链接的 ffmpeg CLI。** 但这条结论**不是**"硬编吞吐实测过关"得来的——本环境只有一台**没有编码器**的 x86_64 模拟器（`/vendor/lib64` 只有解码器模块，`h264_mediacodec` 在它上面返回码 0 却一帧不出），**真机硬编的 1× 实时读数仍未取得**。它站得住的两条腿是：

1. **换路线不是等价替换**：Media3 没有镜像效果、时间窗还得靠 `TextureOverlay` 子类自写（见 Considered Options）——这条理由与吞吐无关；
2. **这条链在 Android 侧没有硬伤，且吞吐风险有梯子兜着**：在目标上跑通了完整滤镜图（全局镜像 + 时间窗局部镜像 + 全分辨率 alpha 贴纸 + 取景裁切缩放 + 拍声混音），产物可播、900 帧一颗不少、整片解码无错；镜像闸门还做了**像素级**验收（窗内像未翻的原片、窗外像翻过的原片，含半开区间的两个端点帧）。软编那一档 1080p 中位 13917ms（2.16× 实时）、720p 10183ms（2.95× 实时），系数 1.37；宿主对照（libx264）1080p 6263ms（4.79×）、720p 5210ms（5.76×）、只跑滤镜图 2824ms。**不足以 1× 实时就降到 720p** 这条降级规则因此没有被触发，也没有被证伪。

**关掉缺口的办法**：在一台真机上跑 `tool/cast_render_bench.sh -d <真机 serial> --runs 3`，读 `h264_mediacodec` 的 1080p/720p 中位墙钟与帧数（同一串命令、同一组判定）。

**换路线的触发条件（写死）**：真机读数显示 **1080p 与降到 720p 都到不了 1× 实时**（中位墙钟大于素材时长），才动 GPU 合成路线；那时**另开一条 ADR**，**不改写本文**——本文里 Media3 的定位本来就是"吞吐不过关时的退路"。投屏渲染**用哪个编码器**（硬编 / 软编兜底）属于实现细节，不重开这条路线的决策；但**降级到 720p 必须在准备面板明说**，那条口径来自规格，不因本文而变。

## 渲染能力与降级（#36 的回填）

**渲染前先问编码器**：投屏准备面板打开即经手写平台通道 `susume/encoder_realtime` 问一句「这台机器的编码器保证 1× 实时吗」。查的是系统给编码器的**性能点**（`MediaCodecInfo.VideoCapabilities.getSupportedPerformancePoints()`，**API 29+**；h264 编码器、硬编优先），问的是「覆盖得了 1920×1080@30 吗」。（**别与「遥控项判据」那一次探测混起来**：起投时问的是接收端的 `GetCurrentTransportActions` **与** `GetVolume`——两问合成一份判据，判据说不显示的那一枚遥控连一条指令都不发；见 `lib/cast/CONTEXT.md` 的「遥控项」。）答案是**三态**，不是 bool：

- **保证** ⇒ 按**源分辨率**渲（链路一个缩放节点都不加）；
- **不保证**（性能点答得出来、但覆盖不了）⇒ **降到 720p**（链尾 `scale=-2:'min(720,ih)',setsar=1`：高度**只降不升**——高过 720 行才钉到 720，取景裁出来**不足 720 行**的选区原样留着，宽度按源画面比例现算，不拉伸；码率 8M → 4M）；
- **问不到** ⇒ 与「不保证」**同一侧**：也降到 720p。

**待定决策（本票唯一）的选定：问不到时按「不可保证」处理，即降级。** 两条理由：

1. **它与上位理由同向**。这门查询存在的意义就是「不足以 1× 实时就降到 720p，宁可降分辨率，也不给用户一个未知时长的进度条」；问不到时若按「保证」处理，等于把最不确定的那一档交给用户去等一条没底的进度条，正好违背这条规矩。
2. **问不到是常态分支，不是边角**。性能点是 **API 29+** 才有的 API，而本仓 `minSdk` 解析为 **24**——API 24–28 的设备上这门 API 根本不存在；再叠上「设备不报性能点 / 通道不在 / 查询失败」，兜底必须有一个**确定的**一侧。取降级这一侧，行为在全部设备上是可预期的：能保证就别降，保证不了（或问不出来）就降到 720p 并把这句话摆在准备面板上。

**分辨率档是渲染参数与缓存键的一维**：`CastRenderRequest` / `CastRenderKey` 多出这一维（键的第三分量），于是同一支舞、同一勾选、同一投屏倍速档，在降级与不降级下是**两份不同的缓存条目**，不得互相命中。只勾声音类 + 1× 档时视频流原样复制（没有可降的编码），此时分辨率档只活在键里、不进命令行，准备面板也**不说**那句降级说明（说「降到 720p」就是假话）。

**明说是硬要求**：降级时准备面板当场出一句「这台机器没法保证 1× 实时渲染：这一份降到 720p，进度才不至于没底」（措辞用「没法保证」而非「不保证」——它同时覆盖「性能点覆盖不了」与「问不到」两支）；不降级时一个字都不多说。

三态 → 分辨率档是一条**纯件**（`lib/cast/cast_encoder_realtime.dart`，可直测）；真机读数与 720p 的核对步骤写在 [`lib/cast/docs/real-device-acceptance.md`](../../lib/cast/docs/real-device-acceptance.md) 的路径 P（`adb logcat -s SusumeEncoderCapability` 读性能点，`ffprobe` 读产物帧尺寸）。
